bug_report
/datum/bug_report

One bug report from one connection, from the moment its form opens to its receipt.

The incident context is frozen in New(), before anything can yield, and only ever goes to the bridge. Everything after goes through the reporting bridge on this machine, one request at a time per report. The window only updates when something here changes, and we poll only while it is open and the report waits on the service.

attachment_call
(operation, attachment_id, body_file, output_file, public_consent, encoding, source, wanted_type)

Runs one attachment operation at the bridge.

The request only ever names files we generated, never a path from the reporter. Arguments:

  • operation - upload, preview, remove or consent
  • attachment_id - the attachment it acts on, which the bridge checks against the draft's
  • body_file - the staged image an upload sends
  • output_file - where a preview is saved
  • public_consent - for consent, whether the image may go public with the issue
  • encoding - base64 when an upload's file holds a capture's base64
  • source - for an upload, where the image came from - view, window or file
  • wanted_type - for a preview, the image type we'd rather have, which a bridge that can't make it ignores

begin_ui_capture
(window_id, replace)

Asks one of the reporter's other TGUI windows for a snapshot of itself.

The window renders it, lets the reporter preview and crop it, then sends it back in small acknowledged chunks that receive_ui_capture() stages. Arguments:

  • window_id - which of the reporter's windows, as the page picked it
  • replace - the id of the picture it retakes, or null for a new one

proc
begin_view_capture
(replace)

Renders the reporter's whole view on the server and adds it to the report as a picture.

It's sliced over ticks, so a big view costs the server some time but never stalls it, and it's held to one render a reporter every BUG_REPORT_VIEW_COOLDOWN, whichever report they're in, and BUG_REPORT_RENDERS_MAX across the server. The render spends the captures allowance when it starts, so one dropped on the way still counts. Arguments:

  • replace - the id of the picture it retakes, or null for a new one

proc
bridge_call
(route, body, /list/headers, body_file, output_file, timeout, history_check)

Sends one request to the reporting bridge and waits for it.

Returns the decoded reply, the response itself for a reply saved to output_file, or null with status saying why. One request runs per report and BUG_REPORT_MAX_REQUESTS across the server, so nothing a reporter does can pile up rust-g jobs. We skip SShttp on purpose, it would log the bearer token and the report text. Arguments:

  • route - the bridge's game route, like action or attachment/preview
  • body - the request body as text
  • headers - headers besides the bearer token
  • body_file - a generated file rust-g sends as the body instead
  • output_file - a generated file rust-g saves the reply into
  • timeout - seconds rust-g waits for the bridge

proc
bridge_reply
(/datum/http_response/response, output_file)

Reads the bridge's answer to one request.

Returns the decoded reply, the response itself for a reply saved to output_file, whose headers say what it holds, or null with status saying why. Only no answer or a 5xx means we couldn't reach the report server. A 4xx is it turning the request down, which sets refused and says why in status, except a conflict, which means the draft moved on. A preview says either on its own card, since the page's line and poll are the draft's and receipt's. Arguments:

  • response - the bridge's answer
  • output_file - the file rust-g saved the reply into, if any

receive_ui_capture
(/datum/tgui_window/window, type, /list/payload)

Takes one message of a capture from its window - its preview showing, a chunk to stage, or the reporter cancelling.

Chunks come in order, each acknowledged before the next, and go straight to a file as the base64 they are. We never decode or hold the image. Returns whether the message belonged to the capture. Arguments:

  • window - the window the message came from
  • type - bug-report/capture-ready, bug-report/capture-chunk or bug-report/capture-cancel
  • payload - the message's decoded payload, a cancel's with the window's reason

proc
upload_picture
(/datum/bug_report_picture/picture, path, encoding, spent)

Uploads a picture's staged image to the bridge and deletes the file, whatever happens.

A retake gives back the picture's last image first, or one a lost reply may have left with the service, so the report never holds more than the service takes. The reporter's own files spend the hourly upload allowance, captures the bigger capture one. Arguments:

  • picture - the picture the image is for, already on the report
  • path - the generated file holding the image, or a capture's base64
  • encoding - base64 for a capture, null for an image file
  • spent - whether its allowance was spent already, as an in-game capture's is when its render starts and a file's when the prompt gives it back
